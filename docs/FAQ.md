# 常见问题解答 (FAQ)

## 通用问题

### Q1: 这个补丁适用于哪些内核版本？

**A:** 主要针对 Linux 2.6.39，理论上也适用于 2.6.38-2.6.40 等相近版本。3.x 及以上内核已经原生支持优化，无需此补丁。

### Q2: 为什么只有 SSD 需要这个补丁？

**A:** HDD 写入速度慢，dirty pages 积累慢，单次 writeback 批次相对较小，锁持有时间短，问题不明显。SSD 写入速度快，容易触发大批量 writeback，导致锁竞争。

### Q3: 可以只使用部分优化吗（比如只用内核补丁）？

**A:** 可以，但效果会打折扣：
- 只用内核补丁：3 workers 可能仍会 hang
- 补丁 + commit=1：3 workers 稳定，5 workers 可能 hang
- 完整方案：3-4 workers 稳定

### Q4: 这个方案会影响 SSD 寿命吗？

**A:** 影响很小（写入量增加 3-5%，寿命损失 <5%）。对于典型使用场景，损失不到 1 年，完全可接受。

### Q5: 如果我的系统使用 HDD，能用这个补丁吗？

**A:** 不推荐。激进的 dirty page 参数会降低 HDD 性能（频繁小写入导致大量寻道）。HDD 系统应该保持默认配置。

## 安装相关

### Q6: 我必须重新编译整个内核吗？

**A:** 不需要。只需要编译 ext4 模块（`make M=fs/ext4`），然后替换即可。

### Q7: 如果编译失败怎么办？

**A:** 常见原因：
1. 内核源码版本不匹配 → 确认 `uname -r` 与源码版本一致
2. 缺少编译工具 → 安装 `gcc`, `make`, `kernel-devel`
3. 源码不完整 → 重新下载内核源码

### Q8: 更新 initramfs 失败怎么办？

**A:** 
- 如果系统有 `dracut`，使用：`dracut -f`
- 如果系统有 `mkinitramfs`，使用：`mkinitramfs -o /boot/initramfs-$(uname -r).img`
- 如果都没有，查看发行版文档

### Q9: 应用补丁后系统启动失败怎么办？

**A:** 恢复步骤：
1. 从 GRUB 选择恢复模式启动
2. 恢复备份模块：
   ```bash
   cp /lib/modules/$(uname -r)/kernel/fs/ext4/ext4.ko.backup \
      /lib/modules/$(uname -r)/kernel/fs/ext4/ext4.ko
   dracut -f
   reboot
   ```

## 配置相关

### Q10: 为什么要用 commit=1 而不是默认的 5 秒？

**A:** commit 间隔决定了单次 journal commit 积累的 dirty data 量：
- commit=5：5 秒积累，单次处理大批量
- commit=1：1 秒积累，单次处理小批量

配合内核补丁，进一步缩短锁持有时间。

### Q11: 可以用 commit=2 或 commit=3 吗？

**A:** 可以，但效果会略差。commit=1 是经过测试的最优值。

### Q12: dirty_ratio 可以设置为 1 吗？

**A:** 不推荐。太小会导致写入进程频繁被阻塞，影响性能。2-5 是合理范围。

### Q13: 这些参数对内存有什么要求？

**A:** 
- 2GB RAM：2% = 40MB dirty pages，完全够用
- 4GB RAM：2% = 80MB dirty pages，绰绰有余
- 建议最少 1GB RAM

## 性能相关

### Q14: 吞吐量会下降多少？

**A:** 根据测试：
- 顺序写：下降 5-10%
- 随机写：下降 3-7%
- 但尾延迟改善 90%+

### Q15: 为什么我的 benchmark 显示性能下降？

**A:** 
- 单进程顺序写可能略慢（大批量改为小批量）
- 但多进程并发场景整体性能更好（避免 hang）
- 实际应用中稳定性的价值 > 轻微的吞吐损失

### Q16: 可以支持多少个并发 I/O 进程？

**A:** 
- 完整方案：3-4 个稳定
- 5 个可能出现卡顿
- 需要更高并发建议升级到 3.x 内核

## 兼容性问题

### Q17: 这个补丁会影响数据一致性吗？

**A:** 不会。我们保持了 ext4 的 ordered 模式，数据一致性与原版相同。

### Q18: 与 LVM/RAID 兼容吗？

**A:** 完全兼容。补丁只修改 ext4 文件系统层，不影响块设备层。

### Q19: 虚拟机中可以使用吗？

**A:** 可以，但需要：
- 虚拟机使用 SSD 后端存储
- 虚拟机内运行 2.6.39 内核
- 在虚拟机内应用补丁

### Q20: Docker/容器环境可以使用吗？

**A:** 可以，但补丁需要应用在宿主机内核上，容器共享宿主机内核。

## 故障排除

### Q21: 应用补丁后仍然 hang 怎么办？

**检查清单：**
1. ✅ 模块版本正确（`modinfo ext4 | grep srcversion`）
2. ✅ initramfs 已更新
3. ✅ 挂载选项包含 commit=1
4. ✅ 系统参数已生效（`sysctl -a | grep dirty`）
5. ✅ delalloc 已启用（没有 nodelalloc）

### Q22: 如何确认补丁是否生效？

**A:** 运行测试：
```bash
stress-ng --iomix 3 --timeout 60s
```

- 如果补丁生效：60 秒后正常完成
- 如果补丁未生效：进程卡住，系统 hang

### Q23: 系统日志出现 ext4 错误怎么办？

**A:** 
1. 检查 `dmesg` 输出
2. 如果是 "bug" 或 "error"，恢复原模块
3. 如果是 "warning"，通常可以忽略
4. 提交 issue 到 GitHub

### Q24: 为什么验证脚本显示某些检查失败？

**A:** 常见原因：
- commit=1 未生效 → 检查 fstab，确认重启
- dirty 参数未生效 → 检查 sysctl 配置文件
- 存储类型为 HDD → 这个补丁不适合 HDD

## 维护相关

### Q25: 内核升级后需要重新编译模块吗？

**A:** 是的。如果内核版本改变（如安全更新），需要重新编译和安装 ext4.ko。

### Q26: 如何监控 SSD 健康状态？

**A:** 
```bash
smartctl -a /dev/sda
```

关注指标：
- Percentage Used < 80%：健康
- Available Spare > 20%：健康
- Media Errors = 0：健康

### Q27: 什么时候应该考虑升级到 3.x 内核？

**A:** 当满足以下任一条件：
- 需要支持 5+ 并发 I/O 进程
- 需要更高的 I/O 吞吐量
- 有条件升级且应用兼容

### Q28: 可以在生产环境使用吗？

**A:** 可以，但建议：
1. 先在测试环境充分测试
2. 准备回滚方案
3. 选择低峰时段部署
4. 部署后密切监控

## 技术深入

### Q29: 为什么批次限制是 1024 页而不是其他值？

**A:** 1024 页 = 4MB，是经验值：
- 足够大：保持合理吞吐
- 足够小：锁持有时间 < 1 秒
- 适合 SSD：4MB 在 SSD 上写入很快

### Q30: 这个补丁与 3.x 内核的优化有什么区别？

**A:** 
- 3.x 内核：全面重构，包括 extent 状态树、细粒度锁等
- 我们的补丁：简化版，只实现批次限制

详见 [TECHNICAL.md](TECHNICAL.md)

### Q31: 为什么不移植更多 3.x 的优化？

**A:** 
- Extent 状态树：需要几千行代码，几乎不可能移植
- 细粒度锁：改动太大，风险高
- 当前方案：投入产出比最优

### Q32: nodelalloc 方案与这个补丁哪个更好？

**A:** 对比：

| 方案 | 稳定性 | SSD 寿命 | 性能 | 复杂度 |
|------|--------|----------|------|--------|
| nodelalloc | ✅ 很好 | ⚠️ 损失 20% | ⚠️ 略低 | ✅ 简单 |
| 本补丁 | ✅ 很好 | ✅ 损失 5% | ✅ 正常 | ⚠️ 中等 |

**建议：** 本补丁更好，但如果实施困难，nodelalloc 也是可接受的。
